01

Conceito e Objetivos

Esta aplicação é um portfólio académico e pessoal desenvolvido em Django no âmbito da unidade curricular de Programação Web. O objetivo principal é reunir, num único espaço web, toda a informação relevante sobre o percurso académico, projetos desenvolvidos, tecnologias aprendidas e competências adquiridas.

💡
Porquê um portfólio?
Um portfólio digital bem construído é um dos melhores ativos para quem procura emprego na área de tecnologia. Permite demonstrar, com exemplos concretos, o que se sabe fazer — muito mais eficaz do que um simples CV.

Funcionalidades previstas

✓ Listagem de todas as entidades (Licenciaturas, UCs, Docentes, Projetos...)
✓ Operações CRUD para Projetos, Tecnologias, Competências e Formações
✓ Interface visual consistente com sidebar de navegação
✓ Carregamento de dados via API da Lusófona
✓ Carregamento de TFCs via ficheiro JSON
✓ Aplicação Escola integrada
✓ Página Making Of (esta página)
✓ Página Sobre a Aplicação
02

Modelação de Dados

Antes de escrever qualquer linha de código, foi necessário pensar em quais as entidades que a aplicação precisaria de armazenar e que atributos cada uma deveria ter. Este processo é chamado de modelação e é feito no papel antes de ser implementado.

Como pensei cada entidade

Licenciatura 1 registo

A entidade mais simples. Representa o curso que estou a frequentar. Decidi incluí-la como modelo separado (em vez de apenas texto) porque permite reutilização e garante consistência — todas as UCs apontam para o mesmo objeto Licenciatura.

nome CharField — nome completo do curso
sigla CharField — ex: "LEI", aparece nos badges
url_site URLField — link para o site da Lusófona
descricao TextField — descrição livre do curso
imagem ImageField — logótipo ou imagem representativa
Decisão: Usar CharField para nome e sigla em vez de apenas um campo, porque a sigla é usada frequentemente na interface (badges, tabelas) e é mais prático ter já calculada.
UnidadeCurricular 22 registos

Representa cada disciplina do curso. Esta foi a entidade que sofreu mais evoluções ao longo do projeto — começou simples e foi crescendo à medida que se descobriram novos dados disponíveis na API da Lusófona.

licenciatura ForeignKey → Licenciatura
nome, sigla CharField — identificação da UC
ano, semestre IntegerField — posição no plano curricular
ects IntegerField — créditos europeus (default 6)
course_code, curricular_unit_code CharField — códigos da API Lusófona
objetivos, programa, metodologia TextField — conteúdo académico
bibliografia, avaliacao, apresentacao TextField — da API
Decisão: Adicionei os campos da API (course_code, curricular_unit_code, objetivos, etc.) numa segunda iteração, após explorar os dados disponíveis. Documentei esta evolução no Making Of porque é importante mostrar que a modelação não é estática.
Docente 23 registos

Representa os professores do curso. A decisão de criar uma entidade separada (em vez de apenas um campo de texto na UC) foi fundamental para poder mostrar a foto e o link para o perfil da Lusófona.

nome CharField — nome completo
email EmailField — contacto
url_lusofona URLField — perfil na Lusófona
foto ImageField — fotografia do docente
Decisão: Inicialmente tinha um campo departamento, mas depois percebi que a ligação mais útil seria a página do docente na Lusófona. Substituí departamento por foto e url_lusofona. Esta mudança está documentada como um dos primeiros erros de modelação identificados.
Projeto 2 registos

A entidade central do portfólio — representa trabalhos realizados nas UCs. É das mais ricas em atributos porque precisa de mostrar tudo o que é relevante para um futuro empregador.

uc ForeignKey → UnidadeCurricular
titulo CharField — nome do projeto
descricao TextField — o que faz o projeto
conceitos_aplicados TextField — o que aprendi
imagem ImageField — screenshot ou imagem
link_github URLField — repositório (muito importante!)
video_demo URLField — demonstração em vídeo
tecnologias ManyToManyField → Tecnologia
competencias ManyToManyField → Competencia
Decisão: O campo link_github foi considerado obrigatório desde o início porque é um dos primeiros elementos que um recrutador técnico verifica. A relação com Tecnologia é ManyToMany porque um projeto usa várias tecnologias e a mesma tecnologia aparece em vários projetos.
Tecnologia 6 registos

Lista de tecnologias aprendidas. Inclui linguagens, frameworks, ferramentas e bases de dados. Tem um campo de nível de interesse para poder mostrar o que domino melhor.

nome CharField — ex: "Python", "Django"
categoria CharField choices — linguagem/framework/ferramenta...
tipo CharField choices — frontend/backend/outros...
descricao TextField — o que faz, o que aprendi
logo ImageField — logótipo oficial
url_site URLField — site oficial
nivel_interesse IntegerField — 1 a 5 estrelas
Decisão: O campo tipo foi adicionado na Ficha 8 para poder agrupar tecnologias por categoria na página Sobre. Sem este campo seria impossível separar Frontend de Backend visualmente.
TFC 529 registos

Trabalhos Finais de Curso de alunos anteriores. Os dados foram carregados a partir de um ficheiro JSON via script Python. É uma entidade de consulta — permite explorar que projetos foram feitos antes e inspirar ideias.

titulo CharField — título do TFC
resumo TextField — descrição
ano IntegerField — ano de realização
link_documento URLField — link para o documento
destaque BooleanField — marcar os mais interessantes
tecnologias ManyToManyField → Tecnologia
Decisão: O campo destaque permite filtrar os TFCs mais interessantes. Com 529 registos é impossível ver todos — este campo resolve esse problema de UX.
MakingOf entidade especial

Esta entidade é única porque documenta o próprio processo de desenvolvimento. É uma espécie de diário de bordo integrado na aplicação — cada entrada descreve uma decisão, um erro ou uma reflexão sobre o desenvolvimento.

titulo CharField — título da entrada
entidade_relacionada CharField choices — qual entidade documenta
descricao TextField — o que foi feito
decisoes TextField — justificações das escolhas
erros_correcoes TextField — bugs e como foram resolvidos
foto_papel ImageField — foto do caderno/papel
uso_ia TextField — como foi usada IA
criado_em DateTimeField — automático
Decisão: O campo criado_em usa auto_now_add=True, o que significa que é preenchido automaticamente quando a entrada é criada — não é editável. Isto garante que a cronologia do Making Of é sempre fiável.
03

Relações entre Entidades

As relações entre entidades são o coração de uma base de dados relacional. No Django, definem-se diretamente nos modelos usando ForeignKey (1:N) ou ManyToManyField (N:M).

ForeignKey — relação 1 para N

Usada quando um objeto pertence a um único outro objeto, mas esse outro pode ter vários.

Licenciatura
──1:N──►
UnidadeCurricular
Uma licenciatura tem muitas UCs. Cada UC pertence a uma só licenciatura.
UnidadeCurricular
──1:N──►
Projeto
Um projeto nasce de uma UC. Cada UC pode ter vários projetos.
Docente (portfolio)
──1:N──►
Curso (escola)
Decisão de reutilizar o modelo Docente da app portfolio na app escola, evitando duplicação de dados.

ManyToMany — relação N para N

Usada quando muitos objetos podem estar relacionados com muitos outros. O Django cria automaticamente uma tabela intermédia na base de dados.

UnidadeCurricular
◄──N:M──►
Docente
Uma UC pode ter vários docentes. Um docente pode lecionar várias UCs.
Projeto
◄──N:M──►
Tecnologia
Um projeto usa várias tecnologias. Uma tecnologia é usada em vários projetos.
Projeto
◄──N:M──►
Competencia
Um projeto demonstra várias competências. Uma competência pode aparecer em vários projetos.
Curso (escola)
◄──N:M──►
Aluno (escola)
Um curso tem vários alunos. Um aluno pode frequentar vários cursos.
⚠️
Problema encontrado com ManyToMany e ordem de declaração:
Ao definir competencias = ManyToManyField(Competencia) dentro da classe Projeto, o Python deu erro porque Competencia ainda não estava definida naquele ponto do ficheiro. A solução foi usar o nome como string: ManyToManyField('Competencia') — o Django resolve a referência depois de carregar todos os modelos.

Arquitetura MVT do Django

O Django usa o padrão MVT (Model-View-Template), que é uma variação do clássico MVC. Compreender este padrão foi essencial para organizar o código corretamente.

🌐
Browser
Faz um GET para /projetos/
→
🗺️
urls.py
Mapeia /projetos/ para projetos_list()
→
⚙️
View
Busca Projeto.objects.all() e passa ao template
→
🗄️
Model
ORM faz SELECT * FROM projeto
→
🎨
Template
projetos_list.html renderiza a lista
→
📄
HTML
Página renderizada devolvida ao browser

O que aprendi sobre o MVT

A grande vantagem do MVT é a separação de responsabilidades. O Model não sabe nada sobre HTML. O Template não faz queries à base de dados. A View é o único ponto de ligação. Isto torna o código muito mais fácil de manter e de perceber.

Exemplo completo — listar projetos
# models.py — define os dados
class Projeto(models.Model):
    titulo = models.CharField(max_length=150)
    uc = models.ForeignKey(UnidadeCurricular, on_delete=models.CASCADE)
    link_github = models.URLField(blank=True)

# views.py — busca os dados e envia ao template
def projetos_list(request):
    projetos = Projeto.objects.all()
    return render(request, 'portfolio/projetos_list.html', {'projetos': projetos})

# urls.py — define a rota
path('projetos/', views.projetos_list, name='projetos_list'),

# projetos_list.html — apresenta os dados
{% verbatim %}{% for p in projetos %}
    <td>{{ p.titulo }}</td>
{% endfor %}{% endverbatim %}

Construção do HTML e Interface

A interface foi construída usando apenas HTML e CSS puro — sem frameworks como Bootstrap ou Tailwind. Esta decisão foi intencional para compreender melhor como funciona CSS e ter controlo total sobre o design.

Estratégia de templates

O Django permite herança de templates com {% verbatim %}{% extends %}{% endverbatim %} e {% verbatim %}{% block %}{% endverbatim %}. Isto significa que criei um base.html com toda a estrutura comum (sidebar, topbar, CSS) e cada página apenas define o seu conteúdo.

base.html — estrutura partilhada
<body>
  <aside class="sidebar">
    <!-- navegação igual em todas as páginas -->
  </aside>
  <div class="main">
    <div class="topbar">{% verbatim %}{% block breadcrumb %}{% endblock %}{% endverbatim %}</div>
    <div class="content">
      {% verbatim %}{% block content %}{% endblock %}{% endverbatim %}  <!-- conteúdo específico de cada página -->
    </div>
  </div>
</body>
projetos_list.html — herda de base.html
{% verbatim %}{% extends 'portfolio/base.html' %}
{% block title %}Projetos{% endblock %}
{% block content %}
<!-- apenas o conteúdo desta página -->
{% endblock %}{% endverbatim %}

Sistema de Design

Defini variáveis CSS no :root para manter cores e espaçamentos consistentes em toda a aplicação:

CSS Variables — paleta de cores
:root {
    --bg:         #f8fafc;  /* fundo da página */
    --bg2:        #ffffff;  /* fundo dos cards */
    --accent:     #0ea5e9;  /* azul principal */
    --text:       #0f172a;  /* texto escuro */
    --muted:      #64748b;  /* texto secundário */
    --sidebar:    #0f172a;  /* sidebar escura */
    --danger:     #ef4444;  /* vermelho para apagar */
    --warning:    #f59e0b;  /* amarelo para editar */
}
🎨
Problema encontrado com texto invisível:
Os templates originais foram criados para um tema escuro (fundo preto) com style="color:#fff" no texto. Quando mudei o fundo para branco, o texto ficou invisível. A solução foi correr um script Python que substituiu todos os color:#fff por color:#0f172a nos ficheiros HTML.
06

Implementação CRUD

CRUD significa Create, Read, Update, Delete — as quatro operações fundamentais sobre dados. Para cada entidade com CRUD, foram criados:

✓ Uma view de listagem (Read)
✓ Uma view de criação com formulário (Create)
✓ Uma view de edição com formulário (Update)
✓ Uma view de confirmação de apagar (Delete)
✓ Um ModelForm que gera automaticamente os campos
✓ Rotas em urls.py para cada operação

Como funciona um formulário Django

forms.py — ModelForm gerado automaticamente
class ProjetoForm(forms.ModelForm):
    class Meta:
        model = Projeto
        fields = ['titulo', 'uc', 'descricao', 'link_github', 'tecnologias']
        widgets = {
            'descricao': forms.Textarea(attrs={'rows': 3}),
            'tecnologias': forms.CheckboxSelectMultiple(),
        }
views.py — Create e Update com o mesmo template
def projeto_create(request):
    form = ProjetoForm(request.POST or None, request.FILES or None)
    if form.is_valid():
        form.save()
        return redirect('projetos_list')
    return render(request, 'portfolio/form.html', {'form': form, 'titulo': 'Novo Projeto'})

def projeto_edit(request, pk):
    obj = get_object_or_404(Projeto, pk=pk)
    form = ProjetoForm(request.POST or None, request.FILES or None, instance=obj)
    if form.is_valid():
        form.save()
        return redirect('projetos_list')
    return render(request, 'portfolio/form.html', {'form': form, 'titulo': 'Editar Projeto'})
💡
Vantagem do Django Forms:
O ModelForm gera automaticamente todos os campos do formulário com base no modelo, incluindo validação. Não precisei de escrever nenhum HTML para os inputs — o Django faz isso com {{ form.as_p }}. Isto poupa imenso tempo e evita erros.
07

Decisões e Justificações

Porquê Django?

Django é um framework "batteries included" — inclui ORM, sistema de templates, admin automático, formulários e autenticação. Para um projeto académico é ideal porque permite focar na lógica em vez de configuração.

Porquê SQLite?

Para desenvolvimento local, o SQLite é mais que suficiente. Não requer instalação de servidor de base de dados e o ficheiro db.sqlite3 fica no repositório, tornando fácil partilhar o projeto.

Porquê CSS puro?

Em vez de Bootstrap ou Tailwind, escolhi CSS puro com variáveis para aprender melhor como funciona. Isto deu-me controlo total sobre o design e evitou dependências externas pesadas.

Porquê duas apps?

Separar portfolio e escola em duas apps Django distintas segue as boas práticas — cada app tem uma responsabilidade clara e pode ser reutilizada noutros projetos.

Reutilizar Docente na Escola

Em vez de criar um modelo Professor separado na app escola, decidi reutilizar o modelo Docente do portfólio. Assim os docentes das UCs podem ser diretamente professores dos cursos.

API da Lusófona

Em vez de inserir manualmente as 22 UCs, criei um script Python que usa a API pública da Lusófona para carregar automaticamente os dados. Isto poupa tempo e garante dados corretos.

Erros Encontrados e Correções

Durante o desenvolvimento foram encontrados vários erros. Documentar estes erros é importante — mostra o processo de aprendizagem e será útil para não repetir os mesmos erros.

NameError ManyToManyField para classe não declarada
Problema: competencias = ManyToManyField(Competencia) dentro de Projeto dava NameError porque Competencia ainda não estava definida naquele ponto do ficheiro.
Solução: Usar o nome como string: ManyToManyField('Competencia'). O Django resolve as referências depois de carregar todos os modelos.
NameError NIVEIS_PROFICIENCIA não definida
Problema: O campo nivel de Competencia referenciava NIVEIS_PROFICIENCIA que não estava definida em lado nenhum.
Solução: Definir NIVEIS = [(i, str(i)) for i in range(1, 6)] dentro da própria classe e usar choices=NIVEIS.
TemplateDoesNotExist Templates em pasta errada
Problema: Os templates estavam em portfolio/templates/ mas deveriam estar em portfolio/templates/portfolio/.
Solução: Criar a subpasta portfolio/ dentro de templates e mover todos os ficheiros HTML para lá com mv portfolio/templates/*.html portfolio/templates/portfolio/.
FieldError Campo inexistente no ModelForm
Problema: O TFCForm tinha destaque nos fields mas o modelo TFC ainda não tinha esse campo.
Solução: Ou remover o campo do form, ou adicionar destaque = BooleanField(default=False) ao modelo e migrar.
Typo Carácter inválido no settings.py
Problema: Na linha 'portfolio', ficou colado um carácter especial ﬁ (ligadura tipográfica), resultando em 'portfolio',ﬁ.
Solução: Abrir o settings.py e remover manualmente o carácter invisível no final da linha.
ImportError portfolioescola juntos
Problema: No INSTALLED_APPS faltava vírgula entre 'portfolio' e 'escola', resultando em ModuleNotFoundError: No module named 'portfolioescola'.
Solução: Adicionar vírgula: 'portfolio', e 'escola', em linhas separadas.

Uso de Inteligência Artificial

Ao longo do desenvolvimento foi usado o Claude (claude.ai) como ferramenta de apoio. O uso foi transparente e está documentado aqui conforme pedido pelo enunciado.

✓ Como foi usado

  • Correção de erros de sintaxe Python
  • Sugestão de atributos para cada modelo
  • Geração dos templates HTML com o design pedido
  • Correção de bugs (NameError, FieldError, etc.)
  • Explicação de conceitos (ManyToMany, select_related, etc.)
  • Script de substituição de cores nos templates

✗ O que NÃO foi feito pela IA

  • As decisões finais de modelação foram sempre minhas
  • A escolha de quais atributos manter ou remover
  • A inserção de dados no admin
  • A compreensão do funcionamento do código
  • Os apontamentos e reflexões do Making Of
🤖
Reflexão sobre o uso de IA:
A IA foi útil para acelerar tarefas repetitivas (criar vários templates com o mesmo padrão) e para diagnosticar erros rapidamente. No entanto, verificou-se que nem sempre o código gerado estava correto — por exemplo, o TFCForm incluía campos que não existiam no modelo. É essencial compreender o código para poder identificar e corrigir estes erros.
